The findings

Five findings, each with a reason and a source.

These are the five finding ids the spec's golden batch is defined to produce. The workbench shows them with the full rule text, evidence object and cited records.

  1. CS01:C-3member-missing · CS-DEMO-1

    Claim C-3 references member M-X, which is not in the member register.

    Source field: claims C-3 → memberId

  2. CS02:C-2member-mismatch · CS-DEMO-1

    Claim C-2 references authorization A-1, which belongs to member M-1, not M-2.

    Source field: claims C-2 → authorizationRef

  3. CS02:C-3unresolved · CS-DEMO-1

    Claim C-3 references authorization A-X, which does not resolve.

    Source field: claims C-3 → authorizationRef

  4. CS03:C-2missing-ref-and-document · CS-DEMO-1

    Claim C-2 requires configured document NOTE-C-2. It is absent from documentRefs and from the document register.

    Source field: claims C-2 → documentRefs

  5. CS04:C-1,C-4exact-duplicate-key · CS-DEMO-1

    Claims C-1 and C-4 share the exact key (M-1, 2026-01-10, VISIT-A, 10000). A duplicate candidate for human review; nothing is deleted or blocked.

    Source fields: C-1 key, C-4 key

Workflow

Four steps, all in one browser tab.

The workbench at app/ is the real tool. This page only shows what it does.

  1. Load

    Pick a bundled synthetic fixture, or import a JSON file up to 1 MiB and 1,000 records. Imports are always labelled UNVERIFIED USER-SUPPLIED DATA.

  2. Validate

    Strict schema first: any schema error rejects the whole batch with a bounded error list and no partial results. Then the four CS-DEMO-1 rules run.

  3. Review

    Filter findings by rule, facet or text. Open one to see its rule version, evidence and cited records. Record a note and decision in a separate layer.

  4. Export

    Download a JSON report or a findings CSV, both carrying the provenance label and rule pack version.

Limits

What this demo is not.

ClaimShield is a vertical slice of four fictional rules, built to show how a preflight review could read.

  • CS-DEMO-1 is fictional. It is not an insurer or payer policy, a coding guideline, a coverage rule or a regulatory requirement.
  • It makes no coverage, medical necessity, coding validity or claim acceptance determination, and does not predict denials.
  • Labels such as SYNTHETIC DEMO DATA only record how data was loaded. They do not detect or prevent real or sensitive data. Do not import it.
  • Findings are candidates for human review. Nothing is blocked, deleted, denied or paid, and there is no live claim processing.
  • Files you supply are unverified. The app has no accounts, no storage and no network requests.
  • Not production ready, and no certification claim. Any real rule would need validation by a qualified billing specialist and a separate privacy and security assessment.
